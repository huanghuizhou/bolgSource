# 什么是RAG（Retrieval-Augmented Generation）

> **RAG** = 检索 + 增强 + 生成

**工作流程**：

- **检索 (Retrieval):** 用户在一堆知识库文档中搜索出最相似的文档块。
- **增强 (Augmentation):** 将检索到的相关文档块与用户查询一起被送入 LLM。
- **生成 (Generation):** LLM 利用提供的上下文生成最终的答案。

# 为什么需要RAG

举个例子： 我在Qwen3大模型上提问，2025年有赞的商业化版本有哪些？

在不联网的情况下，显然大模型没法给出准确答案。Qwen3大模型的训练数据截止到2024年，且Qwen3大概率不会拿有赞企业知识进行训练。

![img](/assets/data/img/rag/image_02.png)

```
💡 有大聪明可能会说：

小A: 那我拿有赞的知识库对大模型进行训练进行微调行不行?
    → 可行但是成本高，且知识库更新，实时同步困难，且微调大模型也不一定准。

小B: 我把整个有赞知识库一起发送给大模型，行不行？
    → 首先大模型不一定能支持那么长的上下文，其次token耗费量会很大，
      执行耗时会很长，而且让大模型基于整个知识库去分析不一定准。
```



大型语言模型（LLM）存在以下局限：

| 局限 | 说明 |
|------|------|
| **知识滞后** | 模型训练数据有截止日期，无法获取最新信息。 |
| **事实幻觉** | 在缺乏确切知识时，模型可能编造看似合理但错误的答案。 |
| **领域知识缺失** | 通用模型对特定垂直领域（如财务、法律、企业内部知识）了解有限。 |

RAG 通过将 LLM 与外部知识库结合，在生成答案前先检索相关文档，有效缓解了上述问题，实现了"**基于事实的回答**"。

> 💡 **个人理解**：RAG本质和Claude Skills以及Agent常用的上下文压缩结构化，做的都是同一件事——
> 只把 <mark>**最必要、最匹配、最有效** </mark>的信息喂给大模型，减少不必要的信息量干扰大模型的判断。
> 既能提高LLM的准确率，也能减少Token的消耗。

## 向量

![img](/assets/data/img/rag/image_05.png)

在RAG当中，实际的的向量维度会有几百甚至几千， 向量维度越多，信息就越丰富，区分度就越高。

![img](/assets/data/img/rag/image_06.png)

举个例子：一个知识文档经过Embedding 解析后获得以下几个分片向量

| 片段文本         | 片段向量                     | 向量相似度 |
| ---------------- | ---------------------------- | ---------------------- |
| 根哥喜欢骑行     | （0.8,1.8,3.4,3.6  ......）  | **0.87**               |
| 根哥喜欢看美女   | （0.9,1.5,3.3,3.5......）    | **0.88**               |
| 有赞本地生活业务 | （-2.8,-0.9,1.2,-4.1 .....） | **0.12**               |

用户搜索 "根哥喜欢什么？"  Embedding 解析后 获得向量 （0.8,1.7,3.3,3.7......）可以发现与前两个分片向量比较接近。

## 相似度算法

| 算法 | 说明 |
|------|------|
| **欧几里得距离** | 测量各点之间的直接距离。这对于总体差异至关重要的密集特征集的聚类或分类非常有用。 |
| **余弦相似度** | 关注向量之间的角度。非常适合文本处理和信息检索，根据方向 (而非传统的距离) 捕获语义相似性。 |
| **曼哈顿距离** | 计算笛卡尔坐标中的绝对差值之和。适用于类网格结构中的路由选择和优化问题。这对于稀疏数据很有用。 |
| **点积** | 两个向量垂直投影的乘积。 |

---

## 召回 (Recall)

召回是指从一个大规模的知识库中，基于相似度算法快速找出与用户查询（query）相关的一组候选文档或段落。

- **目标**：尽可能多地覆盖所有可能相关的文档（**高召回率**），即使其中包含一些不那么相关的噪声。
- **特点**：速度快、可扩展性强，但精度（即相关性）可能不高。

---

## 重排 (Rerank)

重排是在召回阶段得到的候选文档集合基础上，使用更精细、计算成本更高的模型对这些候选结果重新排序，以提升最靠前结果的相关性。

- **目标**：提高排序质量，确保排在最前面的几条结果是最相关、最有用的（**高精度**）。
- **常用方法**：
  - 使用交叉编码器（Cross-Encoder）模型（如 BERT-based reranker），它同时编码 query 和 document，能捕捉更细粒度的语义交互。
  - 商业/开源重排模型：Cohere Rerank、BGE Reranker、ColBERT、RankGPT 等。
- **特点**：计算开销大，通常只对 top-K 召回结果进行重排。

# RAG进阶

## Query改写

再举个例子 某客户使用知识库问答系统场景如下： 

> 客户A: "你个**玩意，我要去哪里查看我的店铺今天赚了多少钱"

通过用户的query，去向量库匹配很难匹配到有用的信息。因为用户的提问是不专业的，和知识库的有效信息相似度过低。

### 单轮 Query 改写

```java
你是一名{domain}领域的专业query改写专家，修改用户的问题，要求如下：
1. 请将以下用户问题改写成符合{domain}行业术语和表达习惯的标准查询
2. 去除用户不必要的情绪
3. 请将以下用户问题改写成一个更清晰、完整、适合信息检索的问题。

用户问题：{query}
```

示例：

![img](/assets/data/img/rag/image_09.png)

### 多轮 Query 改写

```java
根据以下对话历史，将当前用户问题改写为一个独立、完整的查询语句：

对话历史：
用户：我想买一台笔记本电脑。
助手：您对品牌、预算或用途有什么偏好吗？
用户：预算5000左右，主要用来办公。

当前问题：联想有推荐的吗？

改写后：预算5000元左右，主要用于办公，有哪些联想品牌的笔记本电脑推荐？
```

---

### 多视角 Query 扩展（Multi-query Expansion）

让 LLM 生成多个不同角度的查询，提升召回率：

```java
queries = llm.generate(
    prompt="请从不同角度生成3个与以下问题语义相关的检索查询：\n问题：如何提高睡眠质量？"
)
# 输出可能包括：
# - 改善睡眠的方法有哪些？
# - 科学提升深度睡眠的技巧
# - 失眠怎么办？有效助眠建议
```

queries 并行检索，合并结果（去重/重排序）。

## HyDE（Hypothetical Document Embeddings）

![img](/assets/data/img/rag/image_10.png)

HyDE 的核心思想：

1. 让 LLM 先生成一个"**假设答案**"（即使不准确）
2. 用这个假设答案的 embedding 去检索真实文档
3. 本质是将 query 转为"**理想文档**"的语义表示

```markdown
请根据以下问题，生成一段简短的假设性回答（不必准确，但要合理）：
问题：量子计算的基本原理是什么？
假设回答：量子计算利用量子比特（qubit）的叠加和纠缠特性，通过量子门操作实现并行计算……
```

> 💡 HyDE 在某些场景下比直接 query embedding 效果更好。

## A/B 测试（RAG评估）

核心目标是科学评估不同策略（如 query 改写 vs 原始 query、HyDE vs 直接向量搜索、不同检索模型、不同生成模型等）对最终用户体验或业务指标的影响。

### 1. 定义测试变量（A/B组）

- **A组（对照组）**：使用基础RAG配置，如原始query 向量查询、千问3.0模型、BM25检索
- **B组（实验组）**：控制变量引入一个待验证的，如：
  - 检索器：向量检索（OpenAI text-embedding-3-small）替代BM25
  - query是否改写
  - LLM：升级为GPT-4或Claude 3

### 2. 构建评估数据集

### 3. 自动化评估指标

| 指标 | 计算方式 |
|------|----------|
| **平均检索相关性** | 所有样本 Top-1 文档得分的平均值 |
| **Recall@3** | Top-3 中有 ≥1 个相关文档的样本比例 |
| **平均回答质量分** | LLM 对 answer 的 1-5 分均值 |
| **幻觉率** | 幻觉样本数 / 总样本数 |
| **模拟满意率** | "满意"样本数 / 总样本数 |

#### 评估检索结果的相关性（Retrieval Relevance）

判断检索到的文档是否与用户问题相关。

```markdown
你是一个信息检索评估专家。请根据以下标准，对检索结果与用户问题的相关性进行打分：

【评分标准】
- 5 分：文档直接回答了用户问题，包含关键事实或解决方案。
- 4 分：文档高度相关，但缺少部分细节。
- 3 分：文档部分相关，提及了问题中的主题，但未解决核心疑问。
- 2 分：文档弱相关，仅边缘提及关键词。
- 1 分：完全不相关。

【用户问题】
{query}

【检索到的文档内容】
{document}

请只输出一个整数（1-5），不要解释。
```

#### 评估最终回答的质量（Answer Quality）

判断 RAG 生成的回答是否准确、有用、无幻觉。

```markdown
你是一个问答系统评估专家。请根据以下维度对回答进行整体评分（1-5分）：

- 准确性：事实是否正确，是否基于提供的上下文？
- 相关性：是否直接回答了用户的问题？
- 完整性：是否覆盖了问题的核心要点？
- 无幻觉：是否避免编造未在上下文中出现的信息？

【用户问题】
{query}

【参考上下文（检索结果）】
{context}

【系统生成的回答】
{answer}

请只输出一个整数（1-5），其中：
5 = 优秀（准确、相关、完整、无幻觉）
3 = 一般（有部分缺陷）
1 = 差（错误、无关或严重幻觉）

不要输出任何其他内容。
```

#### Prompt（幻觉判断）

```markdown
请严格检查以下回答是否包含"幻觉"——即回答中出现了在参考上下文中**未提及或无法推断**的事实、数据、步骤或结论。

【参考上下文】
{context}

【系统回答】
{answer}

如果回答中的所有信息都能从上下文中直接找到或合理推断，请输出：0  
如果存在任何无法验证或编造的内容，请输出：1

只输出 0 或 1。
```

# 思考

## AI能做什么？

Agent 有两个核心变量：

| 变量 | 说明 |
|------|------|
| **workflow 工作流** | 控制任务走向 |
| **context 上下文** | 控制内容生成 |

### Agent 场景分类

| workflow | context | 说明 | 举例 |
| -------- | -------- | ------------------------------------------------------------ | --------------------------- |
| **确定** | **确定** | 工作流和上下文确定性都很高。这类Agent，AI能发挥的空间很小，AI更多的是粘合剂，做一些优化辅助的功能。感觉这类甚至可以被硬编码代替。 | 一些表单填报Agent |
| **确定** | **不确定** | 工作流固定，但是输入不固定。Agent更多的是在语义理解上发挥作用，固化用户输入，或者是补全用户输入，使LLM生成的结果更符合预期 | 智能客服，技术干预分析Agent |
| **不确定** | **确定** | 工作流不固定，但是输入相对清晰。需要AI去规划路径，需要定义大量Tools，借助AI分析并调用执行Tools。 | 加我智能助手 |
| **不确定** | **不确定** | 工作流和输入都不固定。这是**最复杂，难度最高**的场景，需要工程化程度最高的场景，也是**价值最大**的场景。 既需要借助AI去固化补全上下文，也需要定义大量的Tools，由AI规划路径。 | jira助手 |
